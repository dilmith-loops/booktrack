1. Executive Summary

This engineering document details the comprehensive system optimizations executed to prepare the Sampath Book Finder application for deployment on an AWS Lightsail instance (2 vCPUs, 4GB RAM). The engineering objective was to maximize concurrent user capacity, eliminate database socket starvation, eliminate redundant network calls, and ensure zero-downtime reliability during high-traffic BMICH Colombo International Book Fair visitor surges.

All work was completed strictly adhering to all defined operational guardrails: no remote git pushes (all changes are maintained locally), zero alterations to existing API paths, routes, or schema contracts, and zero hardcoded credentials.

2. System Memory Allocation Model (4GB RAM Budget)

On a 4GB virtual machine, running MySQL 8, PHP-FPM, Redis, Nginx, and system daemons simultaneously requires a rigid memory boundary. Unconstrained worker pools lead directly to out-of-memory kernel panics (OOM killer) or severe SSD swap thrashing. The memory budget was calculated and pinned as follows:

Subsystem Allocated RAM % Budget Technical Configuration & Rationale
MySQL 8.0 Engine 1,400 MB 34.2% innodb_buffer_pool_size = 1400M with 2 instances (1 per CPU core). Keeps all spot, stall, and user tables and indexes resident in RAM; prevents disk IOPS bottleneck.
PHP 8.3-FPM Pool 1,575 MB 38.5% Dynamic pool capped at pm.max_children = 35 (~45MB per worker). Easily sustains 150+ concurrent requests across 2 vCPUs without memory exhaustion.
Redis Cache & Sessions 256 MB 6.3% maxmemory 256mb with allkeys-lru eviction policy. Dedicated to session storage, user status checks, and stall cache.
Nginx & OS Core 500 MB 12.2% Kernel TCP socket buffers, FastCGI keepalive connections, and essential Linux background daemons.
OOM Safety Headroom 365 MB 8.9% Emergency memory buffer protecting against sudden visitor surge spikes and memory spikes during image uploads.

3. Architecture Core Decisions

1. In-Flight Request Deduplication: Multiple frontend components requesting identical resources coalesce into a single HTTP promise, reducing initial socket load by up to 60%.
2. Conditional HTTP 304 Validation: Both stall listings and live spot feeds return an ETag header. Re-sync queries send If-None-Match. When no new content exists, the server returns HTTP 304 with an empty body, freeing the PHP worker in under 2ms.
3. Database IOPS Protection: MySQL's innodb_flush_log_at_trx_commit = 2 flushes transactions to the OS buffer on commit and syncs to disk once per second, preserving SSD health and eliminating I/O bottlenecks.

6. Concurrent Polling Lifecycle Flow

Under the optimized architecture, client polling operates via a high-efficiency tiered path: First, the frontend checks if the tab is visible; if hidden, network dispatch is suspended. Second, if in-flight identical requests are active, the response promise is coalesced. Third, the request arrives at Nginx over HTTP/2 via an active FastCGI keepalive connection. Fourth, PHP executes a single lightweight aggregate check. If unchanged, HTTP 304 is sent immediately with 0 bytes body, freeing the worker pool instantaneously.

9. Production Server Deployment Commands

When deploying to the AWS Lightsail instance, run the following automated commands on the server:

# 1. Apply kernel, PHP-FPM, MySQL, Redis, and Nginx configurations automatically
sudo bash server-config/setup-lightsail.sh

# 2. Warm up Laravel framework caches in the backend directory
cd /var/www/html/backend
composer install --no-dev --optimize-autoloader
php artisan config:cache && php artisan route:cache && php artisan view:cache

# 3. Verify active service health
systemctl status php8.3-fpm mysql nginx redis-server
